#implementation #julia #experiment

> Experiment E-5 on Sophia's side: three candidate keys for a derivative id(D(f)), each computed **without running D**, checked against the derived programs Zygote actually builds (printed by `derivatives.jl`, [[derivatives]]). A key is **sound** if equal keys always mean equal programs (E-5's failure condition is the opposite) and **precise** to the degree that equal programs get equal keys. Source: `derivative.rs`. Results: [[Semantic Boundary Experiments]] §E-5.
>
> Sources: [[AD as a Materialization Case]] (the key `id(D(f)) = H(D, mode, closure, rule world, argument types)`); [[SPEC-006 Worlds, Artifacts and Evidence]] §6a; [[expansion]] (`owners`); [[Review 2026-11-19 Codex B-026 (external)]]. code: `derivative.rs`, `tests/derivatives.rs`, `examples/julia_derivatives.rs`

- **`parse_derivatives`** reads the oracle's lines into an `Oracle`: versions per label (from the run that printed it; a label printed under two version sets goes to `inconsistent`), rule tables and rule facts per label, one `Derived` per gradient with its pieces and whether it is complete (`all`; not `dynamic` or `cut`), the in-session call counts, the piece texts.
- **`Derived::output`**: the derived program's digest, a canonical encoding of its root instance (the gradient's own, the walk's first) and its pieces (instance signature, kind, digest of the text) as a sorted set. Without the root, two functions that reach the same instances would share a program.
- **The closure** of `f` in a package (`Package::closure`): the definitions of `Module.f`, every definition they reference (the crate's `references`, which are in the referrer's id already), and every method of every generic function they use (`uses_generic`), transitively. Per function, not per signature: dispatch is not modelled (E-3's facts would make it per signature).
- **The keys** (`Key`):
  - **`Store`**: D's versions (Julia, Zygote, ChainRulesCore, ChainRules, IRTools), the mode (`Zygote reverse Context{false}`), the argument type, the ids of f's own methods (the root: two functions may share a closure), the ids of the closure's definitions, and the ids of the package's own rule definitions for the closure's functions (definitions of a rule table whose text says `typeof(name)`). Everything except the versions is in the store.
  - **`Rules`**: `Store`, plus every rule method of the session (any module) whose signature names a function of the closure (`typeof(Main.Rules.name)`), with its module and a digest of its body: method-table facts, as E-3's dispatch facts.
  - **`Tables`**: `Store`, plus each whole rule table's digest.
- **`DerivativeLedger`**: one `Row` per gradient (output, keys, closure names and size, f's own ids (`roots`) and the closure's ids (`closure_ids`, used by E-6's facts, [[layers]]), package rules covered, gradient value, completeness); `score(key)` over every pair of rows with complete programs, of one function or two: `unsound` pairs (equal key, different program), `missed` pairs (different key, equal program); `changed(base, label)` and `rekeyed(key, base, label)`: which complete gradients' program or key differ from `base`'s. An incomplete program (runtime dispatch) is not scored: what runs is not known before running.
- A session label (`base+session`) is keyed by the source the session ended with (`rule_g`'s): the caller passes label → package directory.

What it does not do: store anything (a derived record in the store is B-088's question), run Julia, or resolve names outside the package (a rule for `Base.sin` is visible to `Rules` and `Tables` only as a method-table fact, never by the closure, which ends at the package's edge).
